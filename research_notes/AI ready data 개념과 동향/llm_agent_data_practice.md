## 1. Model Context Protocol (MCP): what it is, adoption timeline, tool/data-response design practice, and security

### Takeaway
Between Nov 2024 and Nov 2026 MCP went from an Anthropic-published open protocol to a Linux Foundation–governed standard adopted by OpenAI, Google, Microsoft and AWS, with a major stateless redesign in the 2026-07-28 spec; this moved the "AI-ready data" question from "is the table clean?" to "is the tool/API surface the agent calls well designed?". Documented design practice (few consolidated tools, human-readable fields instead of opaque IDs, concise/detailed response modes, pagination/truncation, actionable errors, output schemas) is mostly vendor engineering guidance with thin published numbers, while the security problems (tool poisoning, prompt injection through tool results, the "lethal trifecta") are well documented and are described by researchers as architectural rather than patchable.

**How MCP reframed "AI-ready data" as tool/API design — documented practice**
- Spec-level structured output (revision 2025-06-18): a tool result may carry `structuredContent` (a JSON object); if a tool declares an `outputSchema`, "Servers MUST provide structured results that conform to this schema" and "Clients SHOULD validate structured results against this schema"; for backward compatibility a tool returning structured content SHOULD also return the serialised JSON in a text block. The spec notes `structuredContent` is server-produced data and is unrelated to LLM "structured outputs" (schema-constrained generation) [P-fetched] — [MCP spec 2025-06-18, Tools](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)
- Spec-level pagination: `tools/list` supports cursor pagination (`cursor` → `nextCursor`) [P-fetched] — [MCP spec 2025-06-18, Tools](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)
- Spec-level content metadata: every content item (text, image, audio, resource link, embedded resource) can carry annotations for `audience` (user/assistant), `priority`, and `lastModified` timestamp; tools may return `resource_link` items (a URI the client can fetch later) instead of inlining data [P-fetched] — [MCP spec 2025-06-18, Tools](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)
- Spec-level errors: tool execution failures are returned inside the result with `isError: true` (so the model can read and react), distinct from JSON-RPC protocol errors [P-fetched] — [MCP spec 2025-06-18, Tools](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)
- Anthropic engineering guidance (2025-09-11), "Writing effective tools for AI agents" [P-fetched, vendor guidance] — [Anthropic Engineering](https://www.anthropic.com/engineering/writing-tools-for-agents):
  - Build a few high-impact tools rather than wrapping every API endpoint; prefer `search_contacts` over `list_contacts`; consolidate multi-step work into one tool (`schedule_event` instead of `list_users` + `list_events` + `create_event`). "Too many tools or overlapping tools can also distract agents."
  - Namespace tools by service/resource (`asana_search`, `asana_projects_search`); whether prefix or suffix naming works better varies by model and should be tested.
  - Return high-signal fields (`name`, `image_url`, `file_type`), not low-level identifiers (`uuid`, `mime_type`); resolving UUIDs to natural-language names or a simple 0-indexed scheme reduced hallucinations and improved retrieval precision (no figure given).
  - Offer a `response_format` enum (`concise` / `detailed`); in the Slack example a detailed response was 206 tokens vs 72 tokens concise (about one-third).
  - Implement pagination, range selection, filtering and truncation with sensible defaults; Claude Code caps tool responses at 25,000 tokens by default; when truncating, tell the agent what to do next (e.g. make narrower searches).
  - Error messages should state the specific fix and show correctly formatted input, not return opaque codes or tracebacks.
  - Describe a tool as you would to a new hire — spell out query formats, terminology and resource relationships; use unambiguous parameter names (`user_id` not `user`).
  - Claims Claude Sonnet 3.5 reached state-of-the-art on SWE-bench Verified after tool-description refinements; held-out accuracy charts for human-written vs Claude-optimised Slack/Asana MCP servers are shown but exact figures are not given in the text.
- Anthropic engineering (2025-11-04), "Code execution with MCP" [P-fetched, vendor guidance] — [Anthropic Engineering](https://www.anthropic.com/engineering/code-execution-with-mcp):
  - Two scaling problems: tool definitions loaded up front can consume hundreds of thousands of tokens before the request is read; intermediate tool results pass through the model (example: a 2-hour meeting transcript adds ~50,000 tokens).
  - Pattern: expose MCP servers as a filesystem of code APIs, let the agent read only the definitions it needs ("progressive disclosure") and filter data in a sandbox; in the article's example token use fell from ~150,000 to ~2,000 (reported as 98.7%).
  - Side benefits: 10,000 spreadsheet rows can be filtered in code before the model sees them; PII can be tokenised before reaching the model. Cost: needs secure sandboxing, resource limits and monitoring.

**Security**
- Spec baseline (2025-06-18): "there SHOULD always be a human in the loop with the ability to deny tool invocations"; clients "MUST consider tool annotations to be untrusted unless they come from trusted servers"; servers MUST validate inputs, implement access controls, rate-limit and "sanitize tool outputs"; clients SHOULD show tool inputs to the user before calling (to avoid exfiltration) and "validate tool results before passing to LLM" [P-fetched] — [MCP spec 2025-06-18, Tools](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)
- Tool poisoning (Invariant Labs, 2025-04-01): malicious instructions embedded in MCP tool descriptions that are "invisible to users but visible to AI models". Demonstration: a poisoned `add` tool made Cursor read `~/.cursor/mcp.json` and `~/.ssh/id_rsa` and pass them out through a parameter; the confirmation dialog did not show the full arguments. Variants: "rug pull" (description changed after approval) and "shadowing" (a malicious server's description alters how the agent uses a different, trusted server's tool — without the malicious tool being called). Suggested mitigations: show full descriptions in UI, pin/hash tool definitions, enforce cross-server data-flow boundaries [P-fetched] — [Invariant Labs, 2025-04-01](https://invariantlabs.ai/blog/mcp-security-notification-tool-poisoning-attacks)
- "Lethal trifecta" (Simon Willison, 2025-06-16): a system combining (1) access to private data, (2) exposure to untrusted content and (3) ability to communicate externally can be made to exfiltrate data; MCP encourages mixing tools from different sources, making the combination easy. Guardrail products claiming to stop "95% of attacks" are insufficient because 95% is a failing grade in security; the only reliable protection for users is to avoid the combination [P-fetched] — [Simon Willison, 2025-06-16](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/)
- Real-world instances: GitHub's official MCP server (May 2025, reported by Invariant Labs — an attacker-written public issue could cause leakage from private repos) and Supabase MCP with Cursor (written up by Willison 2025-07-06; configuring the server read-only removes one leg of the trifecta) **[snippet]** — [Simon Willison, 2025-07-06](https://simonwillison.net/2025/Jul/06/supabase-mcp-lethal-trifecta/); [DevClass, 2025-05-27](https://www.devclass.com/ai-ml/2025/05/27/researchers-warn-of-prompt-injection-vulnerability-in-github-mcp-with-no-obvious-fix/1623458)
- Implementation CVEs: CVE-2025-6514 (CVSS 9.6) in `mcp-remote` allowed a malicious server to run arbitrary commands (JFrog, 2025-07-09); CVE-2025-49596 in Anthropic's MCP Inspector (no authentication by default) [S-fetched] — [Wikipedia](https://en.wikipedia.org/wiki/Model_Context_Protocol)
- 2026 research literature **[snippet — abstracts/summaries only]**: a March 2026 arXiv paper tested seven MCP clients (incl. Claude Desktop, Claude Code, Cursor, Cline) and reports significant issues in most; a January 2026 paper argues the weaknesses are architectural and need protocol-level fixes; OWASP lists tool poisoning as MCP03:2025 in an MCP Top 10; the Cloud Security Alliance published tool-poisoning papers in May and July 2026; a Dynatrace-listed cross-framework study reports a model that verbally identified an attack as prompt injection and still executed the exfiltration call — [arXiv 2603.21642](https://arxiv.org/html/2603.21642); [arXiv 2601.17549](https://arxiv.org/abs/2601.17549); [CSA whitepaper 2026-05-06](https://labs.cloudsecurityalliance.org/wp-content/uploads/2026/05/CSA_whitepaper_mcp_security_tool_poisoning_20260506-csa-styled.pdf); [Dynatrace research](https://www.dynatrace.com/research/publications/mcp-tool-poisoning-in-agentic-ai-frameworks-a-cross-framework-measurement-study/)

### Inferences
- The unit of "AI-readiness" shifted from the dataset to the *interface*: under MCP, what the model actually sees is a tool name, a description, a schema and a response payload, so description quality, field naming and response size become data-quality attributes in their own right.
- The 2026-07-28 changes (stateless core, routing headers, cacheable lists, twelve-month deprecation policy) read as a protocol being hardened for gateway/enterprise operation rather than local desktop use; that is consistent with the governance move to the Linux Foundation in Dec 2025.
- Tool-result data is an attack surface: any free-text field a third party can write (issue bodies, support tickets, document text) is "untrusted content" in Willison's sense. For a data provider, "sanitize tool outputs" and separating read-only from write/egress tools are part of making data agent-ready, not an afterthought.
- Evidence for the design guidance is weak in the scientific sense: the 98.7% token reduction and the one-third concise/detailed ratio are single worked examples in vendor posts, not benchmark results.

- Microsoft's adoption date (commonly associated with Build, May 2025, and Windows/Copilot Studio support) was **not confirmed** in any page read; Wikipedia's article only mentions Semantic Kernel/Azure OpenAI integration (InfoWorld, 2025-05-01).
- Spec revision `2025-03-26` (commonly described as introducing Streamable HTTP and OAuth-based authorization) was not read; no claim about it is made above.
- Current (Nov 2026) registry size and AAIF membership could not be verified from a primary source; only conflicting third-party tracker numbers were found.

## 2. Semantic layers, metric definitions, knowledge graphs and catalogs: evidence that they improve accuracy

### Takeaway
Every study found reports that giving the model explicit business semantics (a knowledge graph, a semantic layer, or even a 4 KB plain-text description of measures and conventions) raises question-answering accuracy over raw schema by roughly 17–40 percentage points, and changes the failure mode from confident wrong numbers to refusals. However the best-known numbers come from vendors on small question sets (dbt Labs: 11 questions; data.world: one insurance schema), newer frontier models have closed much of the raw text-to-SQL gap on those same sets, and a September 2026 ablation suggests the semantic *content* does most of the work rather than the retrieval machinery around it.

### Cited Findings
- data.world benchmark (Sequeda, Allemang, Jacob; arXiv, submitted 2023-11-13): on an enterprise insurance SQL schema, GPT-4 zero-shot question answering reached 16% accuracy directly on the SQL database and 54% over a knowledge-graph representation (ontology + mappings) of the same data [P-fetched; authors are data.world staff per the dbt post below, so **[vendor]**] — [arXiv 2311.07509](https://arxiv.org/abs/2311.07509)
- dbt Labs 2026 benchmark update (Jason Ganz, Benoit Perigaud; 2026-04-07) **[vendor]** [P-fetched] — [dbt Developer Blog](https://docs.getdbt.com/blog/semantic-layer-vs-text-to-sql-2026):
  - Design: the same data.world ACME Insurance dataset (15 tables), 11 questions, each run 20 times; main models claude-sonnet-4-6 and gpt-5.3-codex; baseline GPT-4 (Nov 2023).
  - All questions, original schema — text-to-SQL: 32.7% (2023) → 64.5% (both 2026 models); semantic layer: 60.5% (2023) → 72.7% (both 2026 models).
  - Questions within the semantic layer's modelled scope — text-to-SQL 26.9% (2023) → 62.5% (Sonnet 4.6) / 51.2% (GPT-5.3 Codex); semantic layer 83.1% (2023) → 100% (both).
  - Questions the semantic layer could not express ("too many hops"): semantic layer 0% in 2023 and 2026 (it refuses); text-to-SQL 48.3% (2023) → 70% / 100%.
  - After adding three LLM-generated dbt models: semantic layer 98.2% (Sonnet 4.6) and 100% (GPT-5.3 Codex) vs text-to-SQL 90.0% and 84.1%.
  - Failure mode: text-to-SQL "will cheerfully give you a wrong number"; the semantic layer "tells you it can't answer".
  - Author caveat: text-to-SQL was given the entire schema as context, which "isn't practical for larger datasets". Reasoning-effort settings had little effect on accuracy.
  - Not stated by the authors but visible from the design: no confidence intervals or significance tests, and the publisher sells the semantic layer.
- Paired benchmark (Rumiantsau & Fokeev; arXiv, submitted 2026-04-28): 100 natural-language questions over the Contoso retail dataset in ClickHouse; each of Claude Opus 4.7, Claude Sonnet 4.6 and GPT-5.4 answered every question with schema only and again with schema plus a 4 KB hand-written markdown document of measures, conventions and disambiguation rules. Accuracy 45.5–50.5% without vs 67.7–68.7% with (+17 to +23 points for all three models; all cross-condition comparisons p < 0.01; the three models were statistically indistinguishable from each other in both conditions) [P-fetched, abstract only; author affiliation not shown on arXiv — a secondary write-up attributes it to Cube, **unverified**] — [arXiv 2604.25149](https://arxiv.org/abs/2604.25149); attribution per [Medium: "What the Research Actually Says…"](https://medium.com/@kalingwu/text-to-sql-accuracy-semantic-layer-research-f39f62b952ba) [snippet]
- Ablation of the "context layer" (Qing Ye; arXiv, submitted 2026-09-06): on the DABStep benchmark, four models, four arms, using a YAML "data contract". Hard-task accuracy with vs without the contract's semantic prose: 13.9% → 55.1%, 22.6% → 56.6%, 22.9% → 68.4%, 37.0% → 77.4%. Retrieval scaffolding alone (contract emptied of prose) added 0–5 points on two smaller models and 14–15 points on two frontier models. Pre-compiled views answered all 176 tasks they covered. Delivering the knowledge through the contract beat pasting the same knowledge into the prompt (the contract's fee semantics appeared in generated SQL up to 98% of the time vs 4% for the prompt arm). Ungoverned arms submitted 166 mutating SQL statements; governed arms submitted none. Stated takeaway: "semantics first, scaffolding second, pre-computed macros only where an agent demonstrably fails to derive" [P-fetched, abstract only; single author, no affiliation shown; one benchmark] — [arXiv 2609.22259](https://arxiv.org/abs/2609.22259)
- Open Semantic Interchange (OSI): launched 2025-09-23 by Snowflake with Salesforce, dbt Labs and partners (RelationalAI, Alation, Atlan, Cube, Sigma, ThoughtSpot, Omni, Select Star, Honeydew and others) as a vendor-neutral format for exchanging semantic models between AI and BI tools; 2025-10-28 dbt Labs open-sourced MetricFlow under Apache 2.0 as a reference implementation; 2025-11-13 JPMC, Collibra, Starburst joined; 2026-01-27 the spec went live under Apache 2.0 (Salesforce's post marks it as the official v0.1 release) and AtScale and Qlik joined; 2026-04-28 community update reports 14 new participants; 2026-06-04 a financial-services semantic working group held its first meeting; 2026-07-10 the project entered the Apache Incubator as **Apache Ossie (incubating)**; 2026-08-12 Kyvos joined [P-fetched] — [Apache Ossie updates](https://ossie.apache.org/updates/)
- Databricks is named as a working-group participant in OSI by Salesforce/Tableau posts **[snippet]** — [Tableau blog](https://www.tableau.com/blog/ending-semantic-drift-unified-business-logic-foundation)
- Snowflake Cortex Analyst: Snowflake's accuracy claim is described by third parties as roughly 90% on its own ~150-question internal benchmark, not independently verified **[snippet, vendor claim relayed by third-party blogs]** — [agenticfabriq.com](https://www.agenticfabriq.com/blog/cortex-analyst-vs-genie-accuracy); [valiotti.com](https://valiotti.com/snowflake-cortex-vs-databricks-genie-2026/)
- Databricks Genie: third-party blogs relay Databricks claims of going "from 32% to over 90%" on an internal benchmark, and separately 84.5% first-try correctness; a Databricks worked example reportedly rose from 0% to 100% on 13 questions only after naming, relationships, metrics and rules were added. The two headline numbers differ between sources **[snippet, vendor claims relayed by third parties, unverified]** — [agenticfabriq.com](https://www.agenticfabriq.com/blog/cortex-analyst-vs-genie-accuracy); [typedef.ai](https://www.typedef.ai/resources/semantic-layer-metricflow-vs-snowflake-vs-databricks)
- Scope limits recommended by the vendors themselves, as relayed by third parties: Databricks documents a 50-table limit per Genie space and advises aiming for five or fewer; Snowflake recommends fewer than 10 tables per semantic view; accuracy reportedly drops when spaces exceed ~20 tables **[snippet]** — [colrows.com](https://colrows.com/blogs/snowflake-semantic-views-vs-databricks-metric-views/); [valiotti.com](https://valiotti.com/snowflake-cortex-vs-databricks-genie-2026/)

### Inferences
- Three separate studies with different authors, datasets and model generations (2023 GPT-4; April 2026 and September 2026 frontier models) all point the same direction, which is stronger than any one of them alone — but none is a large, independent, peer-reviewed benchmark, and two of the four are from vendors.
- The gain from semantics did not disappear as models improved, but the *raw* baseline moved a lot (32.7% → 64.5% on the same 11 questions in ~2.5 years). The durable argument for a semantic layer in 2026 is therefore less "accuracy" and more "predictable failure": it refuses instead of inventing a number.
- The April 2026 paper is notable because the "semantic layer" was a 4 KB markdown file, not a product. Together with the September 2026 ablation ("content dominates"), this suggests that writing down metric definitions, conventions and disambiguation rules is the high-value step, and that the delivery mechanism matters less — though the ablation also found a structured contract beat pasting the same text into the prompt.
- The 0% score on out-of-scope questions is the real cost of a semantic layer: coverage is limited to what someone modelled.
- OSI/Apache Ossie indicates the industry now treats metric definitions as an interchange artefact; as of the last update read (Aug 2026) it was an incubating project with a v0.1 spec, so it is early.

### Gaps
- No Spider 2.0 / BIRD figures were retrieved in this session; a third-party headline ("91% in benchmarks, 21% on real data") appeared in search results but was not opened and is not relied on.
- Snowflake's and Databricks' own primary posts with their accuracy methodology were not read; all figures for those two vendors are second-hand.
- A Salesforce page reportedly refers to an OSI "v1.0"; the Apache Ossie updates page does not mention a v1.0 release, so the current spec version is unconfirmed.
- No evidence was found specifically isolating data *catalog* metadata (lineage, ownership, tags) as an accuracy driver, as distinct from metric/semantic definitions.
- The full text (limitations sections) of arXiv 2604.25149 and 2609.22259 was not read — abstracts only.

## 3. Unstructured data readiness: parsing/chunking, the shift from classic RAG to agentic retrieval and "context engineering", llms.txt and Markdown-for-agents, structured outputs

### Takeaway
The 2025–2026 shift is from "retrieve chunks before inference and stuff them in" toward agents that hold lightweight references and pull data just-in-time through tools, with the working assumption that context is a scarce resource that degrades when overfilled. For publishers, the practical conventions are clean Markdown renditions of pages (llms.txt since Sept 2024; HTTP `Accept: text/markdown` negotiation, productised by Cloudflare in Feb 2026), but evidence that major AI crawlers actually consume llms.txt is weak and contested.

### Cited Findings
- Contextual retrieval (Anthropic, 2024-09-19): prepending 50–100 tokens of chunk-specific context to each chunk before embedding and before BM25 indexing cut top-20 retrieval failure (1 − recall@20) from 5.7% to 3.7% (−35%); with contextual BM25 added, to 2.9% (−49%); with reranking, to 1.9% (−67%). Passing 20 chunks beat 5 or 10. For knowledge bases under ~200,000 tokens (~500 pages) the post recommends skipping RAG and putting the whole corpus in the prompt with caching [P-fetched, vendor] — [Anthropic, 2024-09-19](https://www.anthropic.com/news/contextual-retrieval)
- "Context engineering" (Anthropic Engineering, 2025-09-29): defined as "the set of strategies for curating and maintaining the optimal set of tokens" during inference, presented as "the natural progression of prompt engineering". Claims: as tokens grow "the model's ability to accurately recall information from that context decreases" ("context rot"); models have an "attention budget"; context should be treated as finite with diminishing returns. Contrasts "embedding-based pre-inference time retrieval" with just-in-time retrieval, where the agent keeps identifiers (file paths, queries, links) and loads data at run time; trade-off is slower runtime exploration. Recommends hybrid (some data up front, more on demand), compaction, structured note-taking outside the window, and sub-agents that return 1,000–2,000-token summaries after using tens of thousands of tokens. No benchmark numbers given [P-fetched, vendor guidance] — [Anthropic Engineering, 2025-09-29](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Context rot measurement (Chroma technical report; Hong, Troynikov, Huber; 2025-07-14): 18 models from Anthropic, OpenAI, Google and Alibaba. Performance degraded with input length in every experiment, non-uniformly. A single distractor lowered performance and four compounded it. Lower semantic similarity between question and answer passage degraded faster. On LongMemEval (306 prompts), all models scored significantly higher on focused prompts (~300 tokens) than on full prompts (~113k tokens). Counter-intuitively, sentence-shuffled haystacks outperformed coherent ones across all 18 models. Claude models hallucinated least and abstained more; GPT models hallucinated most. Authors' limitations: deliberately simple tasks; mechanism unexplained [P-fetched; Chroma sells a vector database, so **[vendor]**] — [Chroma Research, 2025-07-14](https://www.trychroma.com/research/context-rot)
- NoLiMa long-context benchmark, as quoted by Elastic: at 32K tokens, 11 models dropped below 50% of their short-length baselines **[snippet, second-hand via a search vendor]** — [Elastic Search Labs](https://www.elastic.co/search-labs/en/blog/context-engineering-relevance-ai-agents-elasticsearch)
- Elastic's own tests: models given an entire index as context failed in most cases while an agent with a query tool reached 100%; a retrieval sub-agent design surfaced all needed information in 93.3% of cases with over 40% less context **[snippet, vendor]** — [Elastic Search Labs](https://www.elastic.co/search-labs/en/blog/context-engineering-relevance-ai-agents-elasticsearch)
- llms.txt: proposed by Jeremy Howard, 2024-09-03 (site now at v2, last modified 2026-08-10). A Markdown file at `/llms.txt` (or a subpath) with a required H1 name, a blockquote summary, and H2 sections of annotated links; an "Optional" section marks links an agent may skip when short on context. Pages should also be available as Markdown at the same URL with `.md` appended, discoverable via `rel="alternate" type="text/markdown"` links or HTTP `Link:` headers. Rationale: sites are too large for a context window and HTML carries navigation, ads and scripts that are hard to strip [P-fetched] — [llmstxt.org](https://llmstxt.org/)
- Cloudflare "Markdown for Agents" (2026-02-12): a client sends `Accept: text/markdown`; Cloudflare converts the origin HTML to Markdown at the edge and returns an `x-markdown-tokens` header with an estimated token count plus a `Content-Signal` header (`ai-train=yes, search=yes, ai-input=yes`). Worked example: the announcement post is 16,180 tokens as HTML and 3,150 as Markdown (80% fewer). Claude Code and OpenCode already send the header. Launched as beta for Pro/Business/Enterprise plans [P-fetched, vendor] — [Cloudflare blog, 2026-02-12](https://blog.cloudflare.com/markdown-for-agents/)
- MCP's own documentation site instructs agents to "Fetch the complete documentation index at: https://modelcontextprotocol.io/llms.txt" — an example of llms.txt in production on a standards site (observed 2026-11-25) [P-fetched] — [MCP spec page](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)
- llms.txt adoption and usage are contested **[snippet — third-party blogs, underlying studies not checked]**: one analysis of ~300,000 domains reports ~10% have the file; another blog claims 844,000+ sites as of March 2026; 2026 log studies are reported to show GPTBot, OAI-SearchBot, ClaudeBot and PerplexityBot rarely request `/llms.txt`; Google is quoted as saying it does not use the file; Google's John Mueller is quoted calling Markdown-for-bots "a stupid idea"; one site owner logged 1,381 `Accept: text/markdown` requests in 44 days — [DEV Community](https://dev.to/furqank729/should-you-serve-markdown-to-ai-agents-llmstxt-accept-textmarkdown-and-what-google-actually-53la); [codersera.com](https://codersera.com/blog/llms-txt-complete-guide-2026/); [suganthan.com](https://suganthan.com/blog/cloudflare-markdown-for-agents/)
- One blog states Cloudflare marked Markdown for Agents generally available on 2026-11-09 **[snippet, single source, unverified]** — [ansezz.com](https://ansezz.com/blog/ship-your-own-markdown-for-agents/)
- Structured data in tool results: MCP distinguishes server-produced `structuredContent` validated against an `outputSchema` from LLM "structured outputs" (schema-constrained generation) [P-fetched] — [MCP spec 2025-06-18, Tools](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)

### Inferences
- "More context" stopped being the default answer. The Chroma result (focused ~300-token prompts beat ~113k-token prompts on the same questions) and Anthropic's guidance both argue for delivering less, better-targeted data — which favours queryable interfaces (search, filter, aggregate) over bulk dumps.
- Classic RAG did not disappear; the guidance is hybrid. Anthropic's own 2024 advice to skip RAG under ~200k tokens and its 2025 advice to prefer just-in-time loading are consistent: both treat retrieval as a means of controlling what occupies the window.
- Markdown conventions have a measurable token benefit (80% in Cloudflare's single example) for agents that fetch pages at run time (coding agents already send the header). Their value for *crawler/training/search* ingestion is unproven — the available evidence, though second-hand, leans negative.
- Cloudflare's default `Content-Signal: ai-train=yes` shows that "agent-ready" formatting is entangled with usage-permission signalling; publishers adopting it are also making a licensing statement.

### Gaps
- No primary source was read on document parsing quality (PDF/table/layout extraction) or on chunking-strategy comparisons from 2025–2026; the only chunking evidence here is Anthropic's 2024 post.
- No independent benchmark was found directly comparing classic RAG vs agentic retrieval on the same corpus; the Elastic figures are vendor tests seen only in summary.
- The NoLiMa paper itself was not opened.
- Dates and details of structured-output (JSON-schema-constrained generation) feature launches by OpenAI, Anthropic and Google were not researched in this session; no claim is made.
- No first-party statement from OpenAI, Anthropic or Perplexity on whether their crawlers honour llms.txt was found.

## 4. Data formats and documentation aimed at models: schema descriptions, units/currency/timezone, provenance and "as-of" timestamps, data cards, Croissant

### Takeaway
There is no single dominant "model-facing documentation" standard as of the sources read; what exists is a set of converging mechanisms — JSON Schema descriptions on tool inputs/outputs, per-item metadata such as `lastModified`, plain-text or YAML "data contracts" that state measures and conventions, and dataset-level metadata formats such as Croissant. Direct experimental evidence exists for written conventions/disambiguation rules improving accuracy; I found no study isolating units, currency or timezone annotations specifically.

### Cited Findings
- JSON Schema descriptions as the carrier for field meaning and units: the MCP spec's own `outputSchema` example documents units in the field description ("Temperature in celsius", "Humidity percentage") and states that an output schema helps by "guiding clients and LLMs to properly parse and utilize the returned data" (spec 2025-06-18) [P-fetched] — [MCP spec 2025-06-18, Tools](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)
- Freshness and audience metadata: MCP content annotations include `lastModified` (ISO-8601 timestamp, e.g. `2025-05-03T14:30:00Z`), `audience` and `priority` on any returned content item [P-fetched] — [MCP spec 2025-06-18, Tools](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)
- Cache/freshness at protocol level: since the 2026-07-28 spec, list and resource-read responses carry `ttlMs` and `cacheScope` [P-fetched] — [MCP blog, 2026-07-28](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/blog/content/posts/2026-07-28-spec-ga/index.md)
- Naming: Anthropic recommends unambiguous parameter names (`user_id` rather than `user`), making implicit context explicit (query formats, niche terminology, relationships between resources), and returning semantically meaningful names instead of opaque identifiers (2025-09-11) [P-fetched, vendor guidance] — [Anthropic Engineering](https://www.anthropic.com/engineering/writing-tools-for-agents)
- Written conventions measurably help: a 4 KB markdown document covering "measures, conventions, and disambiguation rules" raised accuracy by 17–23 points across three frontier models (arXiv, 2026-04-28) [P-fetched, abstract] — [arXiv 2604.25149](https://arxiv.org/abs/2604.25149)
- "Data contract" as YAML: in the September 2026 ablation, removing the prose fields from a YAML data contract (keeping tools, allow-list and rules) collapsed hard-task accuracy to 13.9–37.0% from 55.1–77.4% [P-fetched, abstract] — [arXiv 2609.22259](https://arxiv.org/abs/2609.22259)
- Token-count disclosure: Cloudflare returns `x-markdown-tokens` so a consumer can size its context window or choose a chunking strategy before reading (2026-02-12) [P-fetched] — [Cloudflare blog](https://blog.cloudflare.com/markdown-for-agents/)
- Croissant (MLCommons; paper v1 March 2024): a metadata format for ML-ready datasets that leaves data files untouched and adds a descriptive layer in four parts — dataset metadata (name, description, licence; based on schema.org/Dataset), resources (`FileObject`/`FileSet`), record structure, and ML semantics — plus a Responsible-AI vocabulary extension covering data lifecycle, labelling, safety, fairness, traceability and compliance. Version 1.0 shipped a spec, examples and a Python library; early support from Kaggle, Hugging Face and OpenML, loadable via TensorFlow Datasets into TensorFlow/PyTorch/JAX **[snippet — 2024 sources; nothing from 2025–2026 found]** — [arXiv 2403.19546](https://arxiv.org/html/2403.19546v3); [Google Research blog](https://research.google/blog/croissant-a-metadata-format-for-ml-ready-datasets/)
- OSI/Apache Ossie positions governed metric definitions as an exchangeable artefact across AI and BI tools (spec live under Apache 2.0 since 2026-01-27) [P-fetched] — [Apache Ossie updates](https://ossie.apache.org/updates/)

### Inferences
- Croissant addresses a different consumer (ML training pipelines and dataset search) than MCP/semantic layers (an LLM reasoning at inference time). "AI-ready" is used for both, and a report should keep the two meanings apart.
- Because the model reads descriptions, not column statistics, units/currency/timezone and "as-of" time need to appear either in the field description or in the payload itself. The spec offers the slots (`description`, `lastModified`, `ttlMs`) but does not mandate their use, so in practice this is a provider discipline.
- The April and September 2026 results imply the cheapest effective documentation is prose that resolves ambiguity (which revenue? gross or net? which calendar?), i.e. exactly the conventions that are normally tribal knowledge.

### Gaps
- **No source found** that experimentally isolates the effect of unit, currency or timezone annotations, or of explicit "as-of" timestamps, on model accuracy. This is the least-evidenced part of the brief.
- No 2025–2026 update on Croissant (newer versions, adoption numbers) or on data cards/datasheets practice was found; the Croissant material is from 2024 and seen only in search summaries.
- Compact serialisation formats for tabular data in prompts (e.g. CSV vs JSON vs newer token-oriented notations) and any accuracy evidence about them were not researched.
- Provenance standards for model-facing data (e.g. content credentials, lineage in tool responses) were not found in the sources read.

## 5. Evaluation: how teams test whether their data is "AI-ready"

### Takeaway
The working method is empirical rather than checklist-based: build a small fixed set of realistic questions with verifiable answers, run agents against the data/tool surface repeatedly, grade outcomes rather than phrasing, and track token and tool-call costs alongside accuracy. The published academic studies in section 2 are themselves instances of this pattern (paired with/without-context runs on a fixed question set).

### Cited Findings
- Anthropic, "Demystifying evals for AI agents" (2026-01-09) [P-fetched, vendor guidance] — [Anthropic Engineering](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents):
  - Vocabulary: *task* ("a single test with defined inputs and success criteria"), *trial* (one attempt), *grader*, *transcript* (full record incl. tool calls), *outcome* ("the final state in the environment at the end of the trial" — e.g. check the reservation exists in the database, not that the agent said so).
  - Start with 20–50 simple tasks drawn from real failures rather than waiting for hundreds.
  - Grader types: code-based (fast, cheap, reproducible, brittle), model-based (flexible, needs calibration against humans), human (gold standard, slow).
  - Capability evals should start with a low pass rate; regression evals should sit near 100%.
  - Non-determinism: pass@k (at least one of k trials succeeds) vs pass^k (all k succeed); a 75% per-trial rate gives ~42% pass^3.
  - Read transcripts; a 0% pass rate across many trials usually means a broken task. Rigid tool-call-order checks are brittle — grade the outcome.
  - For research/retrieval agents: groundedness (claims supported by retrieved sources), coverage, and source-quality checks.
  - Isolate trials: leftover shared state can inflate scores.
- Anthropic, tool evaluation (2025-09-11): generate realistic tasks that need many tool calls, pair each with a verifiable outcome, run programmatically, and track accuracy, runtime, number of tool calls, token consumption and tool errors; use held-out test sets to avoid overfitting tool descriptions to the eval [P-fetched, vendor guidance] — [Anthropic Engineering](https://www.anthropic.com/engineering/writing-tools-for-agents)
- Retrieval-level metric in use: Anthropic measured retrieval by "1 minus recall@20" (share of relevant chunks missed in the top 20) and advises "always run evals" on chunking/embedding choices (2024-09-19) [P-fetched] — [Anthropic](https://www.anthropic.com/news/contextual-retrieval)
- Paired with/without design: the April 2026 study ran each of 100 questions twice per model (schema only vs schema + semantic document) and reported significance (p < 0.01) [P-fetched, abstract] — [arXiv 2604.25149](https://arxiv.org/abs/2604.25149)
- Repetition and ablation: dbt ran each of 11 questions 20 times per configuration; the September 2026 paper used a four-arm ablation and also reports cost per correct answer and counts of unsafe (mutating) statements [P-fetched] — [dbt blog](https://docs.getdbt.com/blog/semantic-layer-vs-text-to-sql-2026); [arXiv 2609.22259](https://arxiv.org/abs/2609.22259)
- Practitioner guidance from secondary sources **[snippet]**: keep the golden dataset frozen while tuning and change one variable at a time; validate any LLM-as-judge metric against real traces (Google Developers Blog); record per task a start state, expected tool sequence, expected end state and step budget; single-response RAG metrics such as faithfulness miss agent failures (a refund issued on the wrong order is perfectly "faithful" to what was retrieved), so add trace-level metrics such as task completion and tool correctness (DataCamp) — [Google Developers Blog](https://developers.googleblog.com/evaluating-ai-agents-moving-past-the-vibe-check/); [DataCamp](https://www.datacamp.com/tutorial/evaluating-ai-agents)
- Vendor-product evaluation practice **[snippet]**: Databricks' Genie benchmarks reportedly mark an answer correct only if the query result exactly matches the benchmark query's result — [agenticfabriq.com](https://www.agenticfabriq.com/blog/cortex-analyst-vs-genie-accuracy)

### Inferences
- "AI-ready" is testable as a property of a data-plus-interface pair against a named question set and a named model; it is not an intrinsic property of the data. The same data scored 32.7% in 2023 and 64.5% in 2026 with no change to the data.
- The most informative design for a data owner is the paired/ablation one: same questions, same model, with and without the semantic documentation or tool change — it isolates what the data work contributed.
- Cost metrics (tokens, tool calls, latency) belong in the readiness test, because context-bloat failures show up there before they show up in accuracy.
- Refusal rate should be reported separately from wrong-answer rate, since the semantic-layer evidence shows the two trade off.

### Gaps
- No survey or dataset was found on how many organisations actually run such evals, or on typical golden-set sizes in production.
- Standard RAG-evaluation frameworks and their metric definitions (context precision/recall, faithfulness) were not read from primary sources in this session.
- No source proposes a standard, vendor-neutral "AI-readiness score" with published validation; vendor readiness checklists exist but were out of scope and not reviewed here.

## 6. Failure modes

### Takeaway
The documented failures fall into three groups: (a) too little or ambiguous meaning — the model confidently computes the wrong thing; (b) too much or noisy context — accuracy falls as input grows and near-duplicate "distractor" content triggers hallucination; and (c) untrusted content inside the data — instructions hidden in tool descriptions or records hijack the agent. Evidence is strong for (b) and (c) and for ambiguity in (a); for stale data, mixed units/currencies and missing provenance I found mechanisms and guidance but no direct measurements.

### Cited Findings
- Confident wrong answers from raw schema: text-to-SQL "will cheerfully give you a wrong number" with "no guardrail between the question and the generated SQL" (dbt Labs, 2026-04-07) [P-fetched, vendor] — [dbt blog](https://docs.getdbt.com/blog/semantic-layer-vs-text-to-sql-2026)
- Missing business semantics as the dominant error class: without a semantic document, three frontier models reached only 45.5–50.5% on 100 retail analytics questions; the abstract characterises the errors as "confident hallucinations" (2026-04-28) [P-fetched, abstract] — [arXiv 2604.25149](https://arxiv.org/abs/2604.25149)
- Sparse context on hard tasks: with the semantic prose removed, hard-task accuracy was 13.9–37.0% across four models (2026-09-06) [P-fetched, abstract] — [arXiv 2609.22259](https://arxiv.org/abs/2609.22259)
- Coverage cliff: a semantic layer answered 0% of questions outside what had been modelled, in both 2023 and 2026 (dbt Labs) [P-fetched, vendor] — [dbt blog](https://docs.getdbt.com/blog/semantic-layer-vs-text-to-sql-2026)
- Unsafe writes when ungoverned: agents without governance submitted 166 mutating SQL statements; governed arms submitted none (2026-09-06) [P-fetched, abstract] — [arXiv 2609.22259](https://arxiv.org/abs/2609.22259)
- Context bloat / context rot: across 18 models, performance fell as input length grew in every experiment; one distractor reduced accuracy and four compounded it; focused ~300-token prompts beat ~113k-token full prompts on LongMemEval (Chroma, 2025-07-14) [P-fetched, vendor] — [Chroma Research](https://www.trychroma.com/research/context-rot)
- Tool-definition and intermediate-result bloat: loading all tool definitions can cost hundreds of thousands of tokens; a single transcript passing through the model adds ~50,000 tokens (Anthropic, 2025-11-04) [P-fetched, vendor] — [Anthropic Engineering](https://www.anthropic.com/engineering/code-execution-with-mcp)
- Too many or overlapping tools "distract agents"; opaque identifiers (UUIDs) increase hallucination relative to natural-language names (Anthropic, 2025-09-11; no figures) [P-fetched, vendor guidance] — [Anthropic Engineering](https://www.anthropic.com/engineering/writing-tools-for-agents)
- Over-broad scope: accuracy reportedly drops when a Genie space holds 20+ tables or a semantic view covers a broad schema without metric constraints **[snippet, third-party]** — [valiotti.com](https://valiotti.com/snowflake-cortex-vs-databricks-genie-2026/)
- Poisoned metadata and data: hidden instructions in tool descriptions (tool poisoning), post-approval description changes (rug pull), cross-server shadowing (Invariant Labs, 2025-04-01); private data + untrusted content + external communication = exfiltration risk, not reliably stopped by guardrails (Willison, 2025-06-16) [P-fetched] — [Invariant Labs](https://invariantlabs.ai/blog/mcp-security-notification-tool-poisoning-attacks); [Simon Willison](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/)
- Evaluation artefacts that mislead: shared state between trials can inflate scores (an agent read git history from earlier trials); overly strict graders reject valid answers (Anthropic, 2026-01-09) [P-fetched] — [Anthropic Engineering](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)
- Benchmark-to-production gap: the dbt authors concede their text-to-SQL arm received the entire schema, which "isn't practical for larger datasets" — i.e. the reported text-to-SQL figures are optimistic for real warehouses [P-fetched] — [dbt blog](https://docs.getdbt.com/blog/semantic-layer-vs-text-to-sql-2026)

### Inferences
- Sparse context and bloated context are opposite failure modes with the same remedy shape: deliver a small amount of high-meaning context (definitions, conventions) and let the agent fetch the rest on demand. Dumping more raw data fixes neither.
- Near-duplicate or superseded records behave like the "distractors" in the Chroma study: stale versions of a figure sitting next to the current one are a plausible hallucination trigger. This is an inference from the distractor result, not a measured finding about stale data.
- Mixed units/currencies and ambiguous column names are instances of the "missing business semantics" class that the April and September 2026 papers measure in aggregate; neither paper (as far as the abstracts show) reports them as separate categories.
- Better models reduce but do not remove these failures: on the 11-question set, raw text-to-SQL was still wrong about a third of the time in 2026, and stronger models in the Chroma study still degraded with length.
- Security failure is a data-readiness issue because the exploit travels in the data: any provider exposing user-generated text through an agent tool is shipping untrusted content.

### Gaps
- No measured evidence found specifically for **stale data**, **mixed units/currencies**, or **missing provenance** as causes of model error; these remain argued-from-mechanism in the sources read.
- The Chroma report explicitly does not explain why degradation occurs, and its tasks are synthetic/simple; real-task magnitude is unmeasured.
- No incident post-mortems from named enterprises about wrong numbers produced by analytics agents were found.
- Whether the 2026-07-28 MCP spec changed anything about tool-poisoning defences (e.g. signed or pinned tool definitions) is unknown — the release post read does not mention it.
