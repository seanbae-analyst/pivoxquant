# pivoxpolicy

AI 에이전트 관련 **금융 보안 규제·가이드라인을 모아, 같은 잣대로 코딩하고, 바뀐 것을 찾아내는** 연구 도구.
숭실대 학회 발표(2026-11, "AI 에이전트 시대, 금융회사 내부통제는 안전한가")를 저널·컨퍼런스 논문으로 올리기 위해
교수 피드백 — *"한·미 비교 기준이 추상적이다, 수치로 보완하라"* — 에 답하는 숫자를 만드는 것이 목적이다.

> 이 디렉터리는 `pivoxquant` 와 무관한 별도 프로젝트다. 저장소가 없어서 임시로 여기 둔다 — 아래 "별도 저장소로 옮기기".

## 무엇을 재나

**셀 하나 = 문서 × 통제 × 층.** 7개 에이전트 통제(덱 슬라이드 14)를 행으로, 관할(KR·US·EU·INTL)을 열로 놓고
각 칸에 "그 관할에서 그 통제를 요구하는 가장 센 문서의 구속력"을 적는다 — **두 층으로 따로**(코드북 v2, 2026-11-11):

| 층 | 묻는 것 | 점수 |
|---|---|---|
| `analog` 일반 통제 | 문서가 이 통제를 **사람·계정·일반 시스템**을 대상으로 요구·권고하는가 (퇴직자 계정 정지, 결재, 접근 로그…) | 0 미다룸 · 1 자율 · 2 구속력 |
| `agent` AI·에이전트 적용 | 문서가 이 통제를 **AI 시스템·모델·AI 에이전트**를 대상으로 요구·권고하는가 | 0 · 1 · 2 구속력(AI 일반) · **3 구속력 + 에이전트 명시** |

`?` = 문서는 있는데 아직 안 읽음(코딩 필요). 폐지·대체된 문서(`status: superseded`)는 매트릭스에 넣지 않는다.

**왜 두 층인가.** 처음엔 통제마다 '다룸' 한 칸이었다(v1). 발표 덱을 옮긴 1차 코더와 원문을 읽은 2차 AI 코더의 불일치 12칸이
*전부* 같은 물음 — "직원 통제의 유사물(계정 정지 · CISO 승인)이 있으면 에이전트 통제를 다룬 것인가" — 에서 갈렸다(κ 0.70).
교수 피드백 "비교 기준이 추상적" 이 가리킨 곳이 여기다. 두 층으로 나누면 그 물음이 사라지고, 논문의 주장
— *일반 통제는 구속력이 있는데 AI·에이전트에 적용한 요구는 없거나 자율뿐* — 이 **칸 단위 간극**(일반 2 · AI 2 미만)으로 세어진다.

점수는 코더가 직접 매기지 않는다. 코더는 층마다 **true/false/null 과 근거(위치 + 원문 인용)**, AI 층이 true 면 근거 조항의 대상
(`subject: agent` = 에이전트 명시 / `ai` = AI 일반)만 적는다. 문서의 `binding`(0·1·2)은 문서 레코드에 있고, 점수는 자동 계산된다
(`pivoxpolicy/schema.py::cell_score` · `layer_view`). 그래서 코더 둘의 결과를 층마다 그대로 Cohen's κ 로 비교할 수 있다.

- **판정 기준은 `registry/controls.yaml` 하나** — 층 정의, 공통 규칙 G1~G8(범위·요구의 형태·대상으로 층 가르기·증거·경계 사례),
  통제마다 `true_if` / `false_if`. 규칙은 조항 유형으로만 쓴다 — 특정 문서·조문을 이름 붙이면 κ 가 부풀려진다(테스트가 막는다).
- **코더는 같은 원문을 읽는다** — 고정 코퍼스 21건(`snapshots/corpus.json` 에 문서별 출처·범위·sha256). 본문 텍스트는 저작권 때문에
  저장소에 넣지 않는다. ISO/IEC 27001·42001 은 원문이 유료라 코퍼스에 없다(미코딩).
- 빈 양식은 `registry/codings/TEMPLATE.yaml`. v1 코딩(`deck_2026-11-01` · `ai_coder_2026-11-11`)은 기록으로 남기고 그대로 읽힌다.

## 쓰는 법

```bash
cd pivoxpolicy
pip install pyyaml pytest          # 의존성은 이 둘뿐
python3 -m pivoxpolicy.cli check   # 레지스트리·코딩 스키마 검사
python3 -m pivoxpolicy.cli matrix  # 통제 × 관할 — 두 층 나란히 (--layer analog|agent 로 한 층, --csv, --coder)
python3 -m pivoxpolicy.cli gaps    # AI·에이전트 층이 구속력 2 미만인 칸 (옆에 일반 층 점수)
python3 -m pivoxpolicy.cli timeline
python3 -m pivoxpolicy.cli kappa   # 코더 간 일치도 — 층마다 (인자 없으면 두 층 코더 둘, `kappa A B` 로 지정)
python3 -m pivoxpolicy.cli sensitivity      # 칸 하나를 뒤집으면 바뀌는 관할 점수 (◆ = borderline 판정)
python3 -m pivoxpolicy.cli incident-kappa   # 사건 × 통제 코딩 일치도 (v2 코더 둘이 있으면 관점별 κ 도)
python3 -m pivoxpolicy.cli incident-corpus  # 사건 source_url → 고정 원문 + snapshots/incident_corpus.json
python3 -m pivoxpolicy.cli fetch   # 문서 URL 스냅숏 → snapshots/manifest.json, 바뀐 문서 보고
python3 -m pivoxpolicy.cli watch   # 발표 목록 페이지에서 새 글 찾기
python3 -m pivoxpolicy.cli intel   # RSS/Atom/JSON 피드에서 AI 에이전트 관련 새 항목 → snapshots/intel.jsonl
python3 -m pivoxpolicy.cli rubric --check   # 내부통제 평가 루브릭·평가 스키마 검사
python3 -m pivoxpolicy.cli assess example-worked_2026   # 기관 평가 프로필 (단일 등급 없음)
python3 -m pivoxpolicy.cli assess --compare             # 기관 × 차원 격자
python3 -m pivoxpolicy.cli report  # out/ 에 전부 쓰기 (매트릭스·연표·공백·κ·평가 프로필)
python3 -m pivoxpolicy.cli incidents  # AI 에이전트 보안 사건 45건 × 7통제 교차표
python3 -m pivoxpolicy.cli sim     # out/sim.html 모의 테스트 (통제를 켜고 끄며 공격 원형·실제 사건을 다시 돌림)
python3 -m pivoxpolicy.cli site    # out/ 정적 사이트 — index.html 첫 화면 · dashboard.html 대시보드 · sim.html 모의 테스트
python3 -m pytest -q
```

## 첫 화면 (out/index.html, 2026-11-12)

`site` 명령이 대시보드 · 모의 테스트 다음에 낸다(`pivoxpolicy/landing.py`, 템플릿 `landing.html` · `landing.css` · 흐름도 `flow.css`).
연구 노트 형식: 머리말(연구 질문 · 한 문단) → 요약 세 문단과 그림 1(한국·미국·EU × 7통제 × 두 층 작은 매트릭스) →
모의 테스트(그림 2 한 원형을 두 프리셋으로 돌린 흐름도, 그림 3 프리셋별 사건 막힘 막대) → 방법 표(단계 · 하는 일 · 누가 · 지금 규모) → 한계.
**숫자는 전부 빌드할 때 레지스트리에서 계산한다**(손으로 적은 숫자 없음 — `tests/test_landing.py` 가 확인). 스크립트 없음, 폰에서도 읽힌다.
대시보드는 `out/dashboard.html` 로 옮겼다 — 워드마크는 첫 화면으로, 메뉴의 '대시보드' 는 dashboard.html 로.

## 런타임 (프로토타입, 2026-11-12) — 실제 에이전트 등록 · 도구 호출 판정 · 승인 · 즉시 중단 · 레드팀

정적 사이트(`out/`)는 '어떤 통제가 왜 필요한가' 를 평가한다. 런타임은 같은 통제 7개를 **실제 에이전트의 도구 호출에 집행**한다.
표준 라이브러리만 쓴다(WSGI + SQLite) — 의존성은 여전히 PyYAML 하나. 학회 데모 · 실험용이고, 실제 자금이 움직이는 운영에는 별도 보안 검토가 필요하다.

```bash
PIVOX_ADMIN_TOKEN=<16자 이상> python3 -m pivoxpolicy.cli serve        # http://127.0.0.1:8787/admin  (DB runtime.db — 저장소에 올리지 않는다)
PIVOX_AGENT_KEY=pvx_... python3 examples/demo_agent.py                 # 콘솔에서 등록하고 받은 키로 데모 에이전트 실행
```

- **등록부** (`runtime/store.py`): 에이전트(책임자 · 목적 · 종류 · 위험 등급 · 만료 · 환경 · 통제 수준 · 도구 등록부 · 한도 · 위임 관계).
  API 키(`pvx_…`)와 단기 토큰(`pvt_…`, 15분)은 HMAC-SHA256 지문만 저장하고 원문은 발급할 때 한 번만 보여 준다. 키 회전 · 폐기.
- **정책 엔진** (`runtime/policy.py`, 순수 함수): 요청 하나 → 허용 · 거부 · 사람 승인. **AI까지로 켠 통제만 집행**하고 사람·계정까지는 '사람 절차만' 으로 남긴다.
  순서는 모의 테스트의 단계 배치와 같다 — 상태(폐기 · 중단) → 인벤토리(등록부에 있는 도구 · 만료) → 공급자 관리(승인 구성요소 · 버전 · 지문) →
  고유 식별자(단기 토큰 · 등록된 위임) → 최소 권한(도구 권한 · 등록 때 선언한 환경 · 외부 입력 + 고위험 · 고객 범위 · 금액 한도) →
  사람 승인(고위험은 그 요청 그대로 승인된 것만 — 승인 뒤 금액을 바꾸면 다른 요청) → 감사 기록(입력 출처 보존 · 이상 빈도 탐지) → 즉시 중단(탐지 후 자동).
- **승인 대기열**: 승인 화면은 에이전트가 쓴 요약이 아니라 실제 인자와 입력 출처를 보여 준다. 에이전트는 `approval_id` 를 붙여 같은 요청을 다시 보낸다.
- **즉시 중단**: 콘솔 버튼 또는 탐지 후 자동. 살아 있는 토큰을 끊는다. 즉시 중단 통제가 AI까지가 아닌 에이전트는 멈출 수단이 없다고 거절한다(그 통제가 없을 때의 현실).
- **감사 기록**: 해시 사슬(줄마다 앞 줄 해시). 콘솔에서 사슬을 검증한다. 입력 출처와 인자는 감사 기록 통제가 AI까지일 때만 남긴다.
- **레드팀** (`runtime/redteam.py`, `registry/redteam.yaml`): 공격 원형 12개의 실제 호출 순서를 등록된 에이전트의 정책으로 흘려보낸다(복사본에서, 공격자는 승인을 받을 수 없다).
  결과마다 모의 테스트 모델의 예측을 같이 낸다. 둘이 다른 자리가 볼 곳이다 — 예: 모델은 '외부 입력을 읽지 않는다' 고 등록한 에이전트를 공격면 없음으로 보지만,
  런타임은 그 선언을 최소 권한 통제가 켜졌을 때만 집행한다. 사람·계정 층 통제와 '피해 축소' 는 런타임에서 세지 않는다.
- **서버** (`runtime/server.py`): `/v1/token` · `/v1/decide` · `/v1/approvals/<id>` (Bearer), 관리자 `/admin` 콘솔과 `/admin/api/*`
  (세션 쿠키 HttpOnly · SameSite=Strict + CSRF 헤더 + 같은 출처, 로그인 시도 제한, 본문 64KB · JSON 만, CSP script-src 'self', 로그에 헤더·토큰을 남기지 않는다).
- **SDK** (`runtime/sdk.py`): `Guard(url, api_key)` · `guard.check(...)` · `@guard.tool("transfer")` 데코레이터(거부 → `Blocked`, 승인 필요 → `ApprovalRequired`).
- 테스트: `tests/test_runtime.py`(정책 · 저장소 · 서비스 · 레드팀), `tests/test_runtime_server.py`(실제 HTTP 로 로그인 · CSRF · 등록 · SDK · 승인 · 중단 · 레드팀 · 헤더).
- **실제 LLM 에이전트** (`runtime/llm_agent.py` + `examples/llm_agent.py`, Claude Opus 5.5 · 도구 사용): 정산 보조 에이전트가 운영자 지시
  ('금리 뉴스 요약 + vendor-1 에 30만 원 송금')를 처리하다가 숨은 지시가 든 뉴스를 읽는다. 하네스는 **도구를 실행하기 전마다** `/v1/decide` 에 묻고,
  거부면 실행하지 않은 채 이유를 돌려주며, 사람 승인이 필요하면 `--wait-approval` 초까지 기다렸다가 같은 요청에 `approval_id` 를 붙여 다시 묻는다.
  런타임에 닿지 못하면 실행하지 않는다(fail-closed). 입력 출처: 외부 글이 대화에 들어온 뒤의 호출은 그 출처를 달고 가고, 운영자 지시와 인자가
  정확히 같은 호출만 '사람 지시' 로 친다 — 그래서 숨은 지시로 만든 송금은 '외부 입력 + 고위험' 으로 막히고, 시킨 송금은 승인을 거쳐 나간다.
  `--misconfigured` 는 뉴스 속 공지를 따르도록 잘못 설정된 에이전트를 흉내 낸다(모델이 숨은 지시를 따를 때도 런타임이 막는지 보는 용도).
  요청은 `claude-opus-5-5` · effort 명시 · 서버 쪽 대체 모델(`fallbacks: "default"`, 베타 `server-side-fallback-2026-07-01`) · strict 도구 스키마.
  도구는 모두 모의다. `pip install "anthropic>=2.8"`(본체 의존성 아님) + `ANTHROPIC_API_KEY` 가 필요하고, 한 번 돌리면 Claude 호출 3~5회가 청구된다.
  테스트(`tests/test_llm_agent.py`)는 가짜 Claude 응답에 실제 런타임 판정을 붙여 돌린다(API 키 · 비용 없이).
- 배포: 정적 사이트(Vercel)와 따로 돌려야 한다(Render 등). `PIVOX_ADMIN_TOKEN` · `PIVOX_KEY_PEPPER` · `PIVOX_SECURE_COOKIE=1`(HTTPS) 을 환경변수로.
  아직 없는 것: MCP 프록시 방식 연결, 다중 관리자 · 역할, 승인 알림(메일 · 메신저), DB 이중화.

### 진단 도구로 쓰기 (2026-11-12) — 명세 가져오기 · 적용 조문 · 진단 보고서 · LLM 레드팀

회사가 이미 가진 에이전트의 도구 정의에서 출발해, 그 에이전트에 걸리는 조문과 미차단 시나리오를 보고서 한 벌로 낸다.

```bash
python3 -m pivoxpolicy.cli diagnose examples/agent_spec_order.yaml --out out/diagnosis      # 서버 없이 보고서(HTML · MD · RCM CSV · 조문 CSV)
python3 -m pivoxpolicy.cli llm-redteam examples/agent_spec_order.yaml --trials 3            # 실제 모델(키 · 비용 필요)
```

- **명세 가져오기** (`pivoxpolicy/intake.py`, 콘솔 '명세서로 등록'): Anthropic · OpenAI 함수 · MCP `tools/list` 도구 정의를 섞어 받는다.
  도구마다 종류(조회 · 쓰기 · 전송 · 실행 · 송금·주문)를 근거와 확신도와 함께 추정하고(동사 먼저 — `get_order_status` 는 조회, 모르면 쓰기),
  금액 · 고객 인자(`notional_krw`, `customer_id` …), 외부 글을 읽는 도구, 적용성 프로필을 찾는다. 공격 케이스는 **그 에이전트의 실제 도구 이름 · 인자로** 만든다.
  런타임은 도구별 `amount_arg` · `customer_arg` 로 한도 · 고객 범위를 검사한다(예전에는 `amount` · `customer` 라는 이름만 봤다).
- **적용 조문** (`pivoxpolicy/obligations.py`, `registry/obligations/kr-securities.yaml`, 증권 61개): 관할 프리셋('한국 — 강제 규제만')은 적용 조건을 보지 않는다.
  여기서는 조문 하나마다 적용 조건(하는 일 · 정보 · 모델 · 일반투자자 · 자동화된 결정 · 고영향 AI)과 에이전트에 미치는 방식(AI 명시 · 행위 규율 · 주체 확장 해석)을 적고,
  세 기준(명문 기준 / 확장 해석 기준 / 자율규범 포함 기준)으로 통제 수준을 도출한다. 구성상 저촉(예: 개인신용정보를 해외 API로 — 국내 설치 의무)은 따로 표시한다.
  인용은 국가법령정보센터 현행 원문(2026-11-12)이나 이 저장소의 문서 코딩에서 대조한 것만 싣는다. **변호사 검토 전 초안이다.**
- **진단 보고서** (`pivoxpolicy/diagnosis.py`, 콘솔 '진단 보고서'): 요약 · 우선 조치 · 통제 매트릭스(RCM) · 구성상 저촉 · 시나리오 시험(미차단 · 승인 의존 · 단일 보완 통제 ·
  조문과의 관계) · 조문별 충족 · 책무별 미충족(책무구조도 점검 목록) · 도구 추정 · 한계 · 증적. 단일 보완 통제는 하나를 올려 같은 엔진으로 다시 돌려 확인한 것만 적는다.
- **LLM 레드팀** (`runtime/llm_redteam.py`): 회사 에이전트의 시스템 프롬프트와 도구로 실제 모델을 돌린다. 외부 글을 읽는 도구의 결과 · 고객 메시지에
  숨은 지시를 심고, 시나리오마다 N회 반복해 **모델이 따른 비율**(모델 쪽 위험)과 **따랐을 때 런타임이 막은 비율**(통제 쪽 효과)을 나눠 낸다.
  도구는 모의, 판정은 샌드박스 정책 엔진, 승인자는 기본 거부(`--approver approve` 는 속은 승인자). `--max-calls` 로 비용을 막는다.
  테스트(`tests/test_llm_redteam.py`)는 숨은 지시를 따르는 · 거절하는 가짜 모델로 돈다. 이 저장소에서 실제 모델로 돌린 결과는 아직 없다.

## 세 가지 측정 — 혼동하지 말 것

- **통제 × 관할 매트릭스** (`matrix`): *규제·가이드라인이 무엇을 요구하나.* 문서 × 7통제, 구속력 0~3.
- **사건 × 통제** (`incidents`): *실제 AI 에이전트 사건에서 어느 통제가 실패했나.* 45건, 증거 수준(1차·벤더·보도)별로 센다.
  related_controls(1차, finder 판단) 와 `registry/incident_codings/`(2차, 블라인드) 를 `incident-kappa` 로 비교한다 — 아래 '2차 코딩 결과'.
- **내부통제 평가 프로필** (`assess`): *한 금융회사가 공개 자료상 무엇을 하는가.* 기관 × 16차원, 증거 수준 0~3.
  - 16차원 = 7통제(agent_control) + 경고→조치 연결(connection 2) + 모의해킹 4요소(testing 4) + 사고 대응(response 3).
  - **단일 등급으로 뭉치지 않는다.** 차원별 레벨 프로필 + 그룹 분포만. 레벨은 "증거 수준" 이지 "통제 유무" 가 아니다.
  - 실제 기관 평가는 명예훼손·공정성 때문에 시드에 넣지 않았다 — `example-worked_2026` 은 가상 예시다.
  - 설계 근거: `registry/rubric.yaml` (덱 슬라이드 2·14·15 + pivoxmap 평가체계 노트). provisional — 리서치 워크플로가 FSB·OWASP ASI·NCCoE 원문으로 basis 를 채우면 교체.

`pip install -e .` 하면 `pivoxpolicy` 명령으로도 된다.

## 문서 레코드 규칙

- `url` 이 없으면 `url_note` 에 왜 없는지 적는다 ("확인 필요 — …"). `url_verified` 는 **실제로 200 을 받은 날**만 적는다.
- `binding` 0 = 보도자료·보고서(규범 아님, 점수 안 냄) · 1 = 자율 · 2 = 구속력. `doc_type` 과 모순이면 `check` 가 거절한다.
- `names_agents` 는 원문을 안 봤으면 `null`. 추측으로 true/false 를 넣지 않는다.
- `summary` 끝에 **어디서 알았는지**(덱 노트 / 보도 / 원문) 를 `source_note` 로 남긴다.
- 1차 코더 `deck_2026-11-01` 은 발표 덱의 2차 인용을 옮긴 것이다. **`provisional: true`**. 2차 코더 `ai_coder_2026-11-11` 은 원문 기반 — 아래.

## 두 층 코딩 결과 (2026-11-12, `report` 가 out/ 에 다시 쓴다)

|---|---|---|---|
| 일반 통제 | 154 | **0.919** | 6칸 |
| AI·에이전트 적용 | 154 | **1.000** | 0칸 (대상 agent/ai 는 51칸 중 50칸 일치) |

  v2.1 은 공급망 경로 · 통지 실패만 참으로 좁혔지만 '공급자 자신이 주인공이면 false' 때문에 같은 유형(악성 패키지 배포)이 글의 초점에 따라 갈렸다(LiteLLM false · Nx true, 두 팀 일치).
  v2.2 는 그 false_if 를 '하류로 닿은 서술이 없을 때만' 으로 좁혔다 — 이제 LiteLLM · Amazon Q · Cline 도 두 팀 모두 참. 각 단계마다 vendors 칸만 새 블라인드 에이전트가 다시 코딩했다.
  **일치도가 높아도 규칙이 맞다는 뜻은 아니다** — v2.1 의 LiteLLM/Nx 는 두 팀이 일치한 채로 틀린 예다.
- 얇거나 제목과 어긋난 출처 7건을 정리했다(`registry/inbox.md`) — 5건은 출처를 바꾸고 두 팀이 다시 코딩, 2건은 제목을 출처에 맞게 좁힘. 이제 45건 모두 κ 에 들어간다.
- 고유 ID 는 '적은 것만' 에서 두 팀이 stated/inferred 를 자주 가른다(조정 7칸 중 2칸). 수준 정의를 이 통제에 맞게 더 좁힐 여지가 있다.
- 같은 계열 AI 두 팀이다 — 재현성이지 정확성이 아니다.

## 민감도 · 경계 칸 검토 (2026-11-12, `sensitivity`)

`python3 -m pivoxpolicy.cli sensitivity` — 문서 × 통제 × 층 칸을 하나씩 뒤집어 관할 점수가 바뀌는 경우를 센다(`out/sensitivity-*.md`).
조정본 기준 **아래로 21**(그 칸 하나가 점수를 받침) · **위로 62**(그 칸 하나가 true 면 점수가 오름). ◆ = 그 칸 note 에 `borderline:`.

논문에 그대로 쓸 사실:
- **한국 일반 통제 '구속력 2' 는 대부분 전자금융감독규정 제13조 한 조에 기댄다** — 7통제 중 5개(인벤토리 · 고유 ID · 최소 권한 · 감사 기록 · 즉시 중단).
  공급자는 위탁 규정 하나. 미국은 최소 권한 · 사람 승인 · 감사 기록이 NYDFS Part 500 하나에 기댄다.
- 간극 16칸은 모두 '구속력 문서의 AI 층 = false' 라는 부정 판정에 기댄다(위로 표의 KR·US·EU AI 층 행). 그 문서들은 AI 를 이름 붙이지 않으니
  G3 로 false 가 분명하다 — 간극을 닫으려면 'AI 도 정보시스템이다' 류의 확장 해석이 필요하고 코드북은 그걸 막는다.
- 국제(INTL) 점수는 거의 전부 FSB 최종 보고서 한 건에 기댄다(AI 층 7칸 모두).

◆ 9칸 검토 — **판정은 하나도 바꾸지 않았다**:

| 칸 | 결론 | 이유 |
|---|---|---|
| FSB × 인벤토리 (AI) | 유지 true | SP3 'use case and model inventories' 를 활용하라 — agent true_if 'AI 사용사례 목록' 그대로. 에이전트 고유 속성은 사례에만 있어 subject ai |
| FSB × 감사 기록 (일반) | 유지 true | SP11 'monitoring and logging of anomalies and cyber incidents' — 로그 문언이 있다(모니터링만이 아님). AI 위협 대응의 일반 IT 강화라 G3 로 analog |
| FSB × 감사 기록 (AI) · 금융위 가이드라인 × 인벤토리 (AI) · CISA BOD × 즉시 중단 (AI) · 금융위 가이드라인 × 고유 ID (AI) | 유지 | ◆ 는 같은 칸의 **다른 층** note 에서 왔다. 이 층의 근거는 분명하다(에이전트 행위 귀속 기록 · 점검항목 ⑭ 목록 관리 · AI 언급 없음 · 서비스 계정 키 보관은 신원 부여 아님) |

| NYDFS Part 500 × 사람 승인 (AI) | 유지 false | Part 500 은 AI 를 이름 붙이지 않는다 (◆ 는 일반 층 note) |
| FSB × 인벤토리 (일반) | 유지 false | 조정에서 판정한 칸 |

◆ 는 칸 단위라 다른 층 note 의 표시도 잡힌다 — 위 9칸 중 5칸이 그렇다.

## 한 칸 코딩 결과 (v1 — 기록)


블라인드 AI 에이전트 5개(문서 KR·US·EU/INTL 3 + 사건 2)가 1차 코딩·문서 요약·incidents.yaml·out/ 을 보지 않고
원문(law.go.kr 고시·법령 본문, 공식 PDF·HWPX, SEC·NIST·NYDFS 원문)을 읽어 코딩했다.
**같은 모델 계열의 두 판단이다 — κ 는 '입력이 다른 두 AI 판단의 일치' 이지 사람 코더 간 신뢰도가 아니다.** 논문엔 사람 코더 1명을 더한다.

| 측정 | 셀 | κ | 파일 |
|---|---|---|---|
| 문서 × 통제 covered | 80 (둘 다 코딩한 칸) | **0.705** substantial · 점수 κ 0.764 | `out/kappa-*.md` |
| 사건 × 통제 실패 | 315 (45 × 7) | **0.417** moderate | `out/incident-kappa-*.md` |

**문서 불일치 12칸은 전부 같은 방향**(1차 false · 2차 true)이고, 대부분이 *직원 통제의 유사물을 에이전트 통제로 볼 것인가* 다 —
전자금융감독규정 §13①11(인사조치 시 계정 정지) = 즉시중단? · NYDFS §500.15(b) CISO 서면 승인 = 사람 승인? · CISA BOD 22-01 FAQ 의 자산 격리 = 즉시중단?
`controls.yaml` 은 통제마다 `employee_analog` 와 `agent_requirement` 를 둘 다 적지만 **어느 쪽이 '다룸' 인지 판정 규칙이 없다**(교수 피드백 '비교 기준이 추상적' 과 같은 지점).

- 그래서 관할 점수가 판단에 따라 갈리는 칸이 **6** (`out/matrix-diff-*.md`): KR 인벤토리 0→2 · 사람승인 1→2 · 즉시중단 1→2, US 고유ID 1→2 · 사람승인 0→2 · 즉시중단 0→2.
  덱의 'US 사람승인·즉시중단 0' 은 엄격한 읽기(agent_requirement)에서만 성립한다.
- **코더와 무관하게 남는 것**: 어느 관할에도 점수 3(구속력 + 에이전트 명시)이 없다. 에이전트를 이름 붙인 요구는 자율 문서(금보원 평가기준 · NIST NCCoE · FSB)에만 있다.
- 사건: 두 코더가 모두 실패를 본 사건 — 최소권한 **18** · 사람승인 **9** · 공급자 8 · 고유ID 6 · 즉시중단 2 · 인벤토리 1 · 감사기록 **0**.
  1차의 '감사기록 20 · 즉시중단 14' 는 2차에서 2 · 2 — 2차는 원문이 그 통제의 실패를 *적어야* 참으로 봤고, 1차는 '로그로 못 찾았다' 류를 추론했다. 이 둘도 판정 규칙(원문 명시 vs 추론)을 먼저 정해야 한다.
