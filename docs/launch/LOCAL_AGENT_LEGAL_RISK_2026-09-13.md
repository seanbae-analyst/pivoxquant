## 0. 한 줄 결론

**형사·약관 리스크는 낮고, 가장 큰 미확정 쟁점은 "우리 서버가 push된 체결을 저장·통합하는 순간 마이데이터업이 되는가"다.** 이 하나는 변호사 답 없이는 Phase 2를 공개하지 말고, Phase 1(파일·스크린샷)은 같은 쟁점을 공유하지만 국내 선례(수기 입력 포트폴리오 앱)가 있어 먼저 가도 된다.

## 2. 해석: 왜 마이데이터 쟁점이 Phase 1에도 걸리는가

경로 1(CSV·스크린샷)과 경로 2(로컬 CLI)는 **서버 관점에서 동일**하다 — 둘 다 "유저가 보낸 본인 체결을 저장하고 여러 증권사분을 한 화면에 보여준다". 차이는 유저 쪽에서 파일을 손으로 뽑느냐 프로그램이 뽑느냐뿐이다. 따라서:

- 마이데이터 해당성이 "예"라면 Phase 1도 같이 죽는다. 하지만 수기 입력·파일 업로드 포트폴리오 앱이 허가 없이 다수 운영되고 제재 사례가 없다는 점이 Phase 1의 실무적 방패다.
- Phase 2가 추가로 지는 리스크는 **접근매체·배포자 책임**인데, 이건 조사 결과 낮다.
- 결국 Phase 2 고유의 법적 리스크는 작고, **공유 리스크(마이데이터)를 변호사가 어떻게 보느냐**가 둘 다의 운명을 정한다.

## 2-b. 최대 보수 평가 (CEO 요청, 2026-09-13)

§1의 판정은 "판례 없음"을 "낮음"으로 적은 곳이 있다. 가장 보수적으로 다시 매기면:

| 축 | §1 판정 | 최대 보수 판정 | 이유 |
|---|---|---|---|
| 접근매체 위임 | 낮음 | 낮음~중 | 인용 판례(2021도6965)는 보이스피싱 통장 대여 사건 — 사실관계가 다르다. 형사 리스크와 별개로 토스가 §5②로 **유저의 API 이용 중지·사고 시 면책**할 계약 리스크는 남고, 이건 우리가 아니라 유저가 진다 |
| 배포자 책임 | 낮음 | 불명 | 판례 없음 ≠ 안전 |
| 마이데이터 | open | **적용된다고 가정하고 설계** | "사업자가 소프트웨어를 제공해 수집하게 했으니 실질적으로 사업자가 수집"이라는 실질 판단 논리가 가능. 우리가 CLI를 배포하면 이 논리에 더 취약 |

**"토스로만"은 리스크를 줄이지 않는다.** 토스 약관이 앱키=접근매체 명시 + 법인 배제로 가장 엄격하고, KIS는 공식 AI 에이전트 확장을 배포할 만큼 서드파티 도구에 관대하다. 로컬 도구를 한 곳으로 좁힌다면 KIS가 더 안전하다. 파일·스크린샷 경로는 증권사와 무관하다.

**보수형 결론**
1. Phase 1(CSV·스크린샷)은 **현 제품 대비 새 법적 표면이 사실상 0** — 지금도 유저가 복수 증권사 거래를 수기로 넣고 우리가 한 화면에 보여준다. 입력 방법만 바뀐다. 엄격한 마이데이터 해석이 이걸 잡는다면 현재 수기 입력도 이미 잡힌 것이다.
2. Phase 2는 **CLI를 우리가 배포하지 않는 형태**로 바꾼다: 가져오기 파일 규격(JSON 스키마)만 공개하고, 기존 커뮤니티 도구(tossinvest-cli, python-kis 등)의 출력을 업로드하게 한다. 키를 만지는 소프트웨어를 만들지도 배포하지도 않으므로 접근매체·배포자·실질 수집 논리가 전부 우리 밖으로 나간다. 개발자 유저의 자동화는 그대로 얻는다.
3. 기록 전용 MCP는 키를 만지지 않아 Phase 1과 같은 지위이나, 타사 주문 MCP와의 결합 책임(Q-MCP)이 미확정이므로 변호사 답 이후.

## 3. 결정

| 항목 | 결정 |
|---|---|
| Phase 1 (CSV·스크린샷) | **진행.** 개인정보 체크리스트(§5) 포함해서 빌드 |
| Phase 2 (CLI·MCP) | **보수형(§2-b)으로 변경: 자체 CLI 배포 안 함.** 가져오기 JSON 스키마 공개 + 커뮤니티 도구 출력 업로드. MCP는 R1 Q-MCP 답 이후. 운영자 본인 dogfooding은 기존 `services/toss` 와 같은 지위라 무관 |

## 4. R1 변호사 질문 (기존 Q10 옆에 추가)

- **Q10-b.** 정보주체 본인이 (a) 직접 업로드한 파일, (b) 본인 기기에서 실행한 오픈소스 소프트웨어가 전송한 데이터를, 당사 서버가 저장하고 복수 증권사분을 한 화면에 표시하는 것이 신용정보법 §2 9의2 "통합하여 제공하는 것을 영업으로" 에 해당하는지. 시행령·감독규정의 "사업자에게 접근·조회·관리 권한이 없는 경우 제외" 취지 조항(정확 조번호 확인 요청)이 이 구조에 적용되는지.
- **Q10-c.** "영업으로" 요건에서 무료·클로즈드 베타가 영업인지, 사업 개시 전 단계로 보는지.
- **Q10-d.** 전자금융거래법 §6③ "사용 위임"이 대가 유무와 무관한 별도 금지 유형인지, 대법원의 "대여" 축소 해석(2021도6965) 논리가 무료·본인 PC 실행에 유추되는지. 배포자에게 §49 또는 방조 법리가 적용될 요건(고의·영리성).
- **Q10-e.** 토스 약관 §5②와 토스 자신의 LLM 연동 홍보(2026-08-13) 사이의 모순을 "토스가 허용한 사용법과 동일 구조"로 항변할 때의 실효성.
- **Q10-f.** 당사가 신용정보법 §2 7호 "신용정보제공·이용자"에 해당하지 않는다는 논리(단일 소스·본인 직접 제공·신용도 판단 미목적)가 유지되는지, 아니면 정보 성격만으로 §20의2 보유기간 등이 부수 적용되는지.
- **Q6-b.** §6 투자자문·일임업 성립에 유상성이 요건인지 — 무료가 §101은 배제하더라도 §6까지 배제하는지.
- **Q-EMAIL.** 이용자가 증권사 체결통보 이메일을 당사의 이용자별 수신 주소로 **자동 전달**하도록 본인 메일 필터를 설정하고, 당사가 본문(계좌번호 포함)을 파싱해 종목·수량·단가·시각만 저장하고 원문을 즉시 폐기하는 구조 — 정보주체 직접 제공으로 보는지, 계좌번호 수신 자체에 추가 의무가 있는지, 마이데이터 "통합" 판단에 영향이 있는지. (ACCOUNT_SYNC_STRATEGY_V2 §Phase 2 v3-C)
- **Q-PAT.** 이용자 소유 자동화(MacroDroid 등)가 개인 액세스 토큰으로 당사 웹훅에 알림 텍스트를 보내는 구조에서, 당사가 배포하는 것이 "설정 템플릿 파일"뿐일 때 배포자 책임·실질 수집 논리가 적용되는지.
- **Q-MCP.** 기록 전용 MCP 제공자가, 유저가 같은 AI에 붙인 타사 주문 MCP의 행위에 대해 "결합 위험을 알고 방치"로 책임질 여지와 약관·고지 방어선.

## 5. Phase 1부터 적용할 개인정보 구현 체크리스트

1. 업로드 흐름에 **명시적 옵트인 체크박스** — 수집 항목(종목·수량·단가·시각, 스크린샷의 경우 계좌번호 일부·잔고 이미지)·목적·보유기간·파기 명시. "본인이 올렸으니 동의" 로직 금지.
2. 스크린샷 원본 **미저장, 파싱 즉시 파기** — 처리방침에 그대로 적는다. 계좌번호는 추출하지 않고, 부득이 추출 시 저장 전 암호화 + 뒤 4자리 표시.
3. **Render 리전 확인** — 미국이면 처리방침에 국외이전 항(이전국·항목·목적·보유기간·연락처) 신설. §28의8 개정(2023-09) 후 계약이행 목적 위탁·보관은 사전 고지로 가능하나, 명시 동의가 안전한지 R1 Q-D1으로.
4. 개인정보처리방침 "수집 항목"에 *이용자가 직접 업로드하거나 이용자 실행 소프트웨어가 전송한 거래 정보* 추가.
5. 정보주체 1만 명 미만 1인 사업자는 내부관리계획 수립 생략 가능(고시 2023-6호) — 단 **암호화 의무는 그대로**.
