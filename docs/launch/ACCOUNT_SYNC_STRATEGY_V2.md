## 2. 문제 재정의

유저가 불편한 건 **"기록"이 아니라 "옮겨 적기"**다.

- 체결 숫자(종목·수량·단가·시각)는 증권사 앱에 이미 있다. 이걸 손으로 다시 치는 건 순수 마찰.
- "왜 샀는가"(thesis)는 증권사에 없다. 이건 PivoxQuant가 존재하는 이유이고, 자동화하면 안 된다.

따라서 목표는 "전부 자동 동기화"가 아니라 **숫자는 자동, 생각은 수기**로 분리하는 것. 이 분리가 되면 제품 철학(멈춤 → 기록 → 거울)과 충돌하지 않고, 오히려 강화된다: *체결은 기록이 아니다. 왜를 붙여야 기록이 된다.*

## 3. 법적 지형도 (사실 기준, 자문 아님)

핵심 경계선은 하나다: **유저의 증권사 인증정보(앱키·토큰·세션)가 PivoxQuant 서버에 닿는가.**

## 5. 추천: 3단계

### Phase 1 — Import Inbox + 파일·스크린샷 (2~3주, 법적 확인 불필요)

1. **공통 파이프라인** (모든 소스가 여기로 합류)
   - `import_batches(id, user_id, source ENUM[csv,screenshot,agent,mcp], broker, raw_hash, status, created_at)`
   - `pending_trades(id, batch_id, ticker, name, action, shares, price, currency, traded_at, dedupe_key, confidence, status ENUM[pending,approved,rejected,duplicate])`
   - `dedupe_key = sha256(user_id|ticker|action|shares|price|traded_at 분 단위)` — 재업로드·중복 스크린샷 방어
   - 승인 API: `POST /api/portfolio/imports/{batch}/approve` — thesis 필수(빈 문자열 거부), 기존 `POST /trades` 로직 재사용
2. **O1 CSV 파서**: 한투 · 토스 · 키움 3개 포맷 먼저 (헤더 시그니처로 자동 감지). 미인식 포맷은 LLM으로 컬럼 매핑 후 유저 확인. export 코드(`routes/profile.py:1711-`)의 역방향.
3. **O2 스크린샷**: 모바일 공유 시트 → `/import` → 비전 모델로 체결 필드 추출 → Inbox. 계좌번호·잔고 영역은 추출 즉시 이미지 파기, 원본 미저장(개인정보처리방침 한 줄 추가).
4. **UI**: `/journal`에 "가져온 체결 N건 — 왜 샀는지 적어주세요" 카드. Inbox 항목은 `/mirror`에 반영되지 않는다(또는 회색). 이 규칙이 차별점이므로 카피에 명시.

### Phase 2 — 로컬 에이전트 + MCP (2~4주, R1 Q10-b 답 이후 공개)

> **2026-09-13 보수형으로 수정**: 아래 2번 `pivox-sync` CLI는 **자체 배포하지 않는다.** 대신 가져오기 JSON 스키마(`source=agent` 페이로드 규격)만 공개하고, 커뮤니티 도구(tossinvest-cli, python-kis 등)의 출력을 유저가 업로드하게 한다. 키를 만지는 소프트웨어를 우리가 만들지 않는 것이 접근매체·배포자·"실질 수집" 논리를 전부 피하는 유일한 형태다. 근거: [LOCAL_AGENT_LEGAL_RISK_2026-09-13.md](LOCAL_AGENT_LEGAL_RISK_2026-09-13.md) §2-b.

1. **PivoxQuant MCP 서버**(O3'): 도구 3개면 충분 — `list_pending_trades`, `record_trade(ticker, action, shares, price, traded_at, thesis)`, `get_positions`. 인증은 유저별 **Personal Access Token**(설정 화면에서 발급·폐기). 토스 MCP는 이미 커뮤니티에 여러 개 있으니(tossinvest-mcp 등) 유저는 둘을 나란히 붙이면 된다.
2. **`pivox-sync` CLI**(O3): 오픈소스(MIT), `pip install pivox-sync`. 키는 로컬 keychain에만. 토스 공식 API는 토큰에 스코프가 없으므로 `services/toss/client.py`의 GET allowlist 패턴을 그대로 이식해 **주문 경로 호출 자체를 코드에서 차단**. 하루 1회 체결 조회 → PivoxQuant `POST /api/portfolio/imports` (source=agent).
3. 서버는 여전히 키를 모른다. 개인정보처리방침에 "이용자가 직접 실행하는 소프트웨어가 전송한 거래 정보"로 명시.

**iOS의 솔직한 한계**: iOS 단축어에는 알림 트리거가 없다. 이메일 체결통보를 안 주는 증권사(토스는 앱 푸시·알림톡 위주로 확인, 이메일 미확인)는 iOS에서 2탭 공유가 남는다.

**한투 이메일 체결통보 실측(2026-09-13, truefriend.com 거래결과통보 안내)**: 이메일 본문 = 계좌번호·종목명·매도/매수·체결수량·체결단가·체결일시. C 파서에 충분하다. 알림서비스 신청 메뉴에서 설정.

**순서**: A(1주) → B 템플릿(2일) → C(1~2주, 인바운드 메일 인프라 비용 0원 여부 먼저) → D·E는 변호사 답 이후. A가 B·C·D 전부의 입구라 먼저다.

**추가 리스크와 방어**
- PAT 유출 → 가짜 체결이 Inbox에 들어옴. 방어: 승인 없이는 기록 안 됨, 토큰 즉시 폐기, 토큰당 일일 건수 제한, 발급 시 "이 토큰은 가져오기만 할 수 있다" 고지.
- C 이메일에 계좌번호 포함 → 파싱 즉시 폐기, 원문 미저장, 로그 마스킹, 처리방침 수집 항목에 "이용자가 전달한 체결통보 이메일" 추가.
- B 템플릿이 카카오톡 알림을 읽는 형태가 되면 유저 기기의 다른 알림도 읽을 수 있는 권한 → 템플릿은 앱·키워드로 좁게 잠그고, 안내에 권한 범위를 명시.

### Phase 3 — 공식 제휴 (사업자등록 + R1 이후)

- 토스증권 Open API는 2026-05 사전신청 → **2026-08-13 정식 출시**(서울경제 보도, ChatGPT·Claude 연동을 공식 홍보). 제3자 파트너 트랙은 미공개이고 약관 §5④가 법인을 배제하므로 **파트너 제안서**로 접근한다(무료·읽기 전용·기록 도구라는 포지션이 협상에 유리). KIS는 자체 GitHub에 AI 에이전트 확장(`kis-ai-extensions`)을 배포 중이라 로컬 도구 방향과 결이 맞는다.
- KIS는 "법인 + 제3자 서비스 제공 시 관련 규정" 트랙이 있다. 사업자등록 후 문의.
- 제휴 확정 전엔 `broker_connections` 테이블(암호화 컬럼 완비)을 되살리지 않는다. 테이블은 그대로 두되 마이그레이션으로 삭제하지도 않는다.

## 6. R1 변호사 질문에 추가할 항목

> 2026-09-13 4축 법적 조사 결과와 확장된 질문 목록은 [LOCAL_AGENT_LEGAL_RISK_2026-09-13.md](LOCAL_AGENT_LEGAL_RISK_2026-09-13.md). 요지: 접근매체·배포자·투자일임 리스크는 낮고, **최대 미확정 쟁점은 push된 체결의 저장·통합이 마이데이터업인가** — Phase 1과 공유되는 쟁점이다.

기존 Q10은 "서버가 OAuth로 포지션 조회"만 묻는다. 이번 전략의 경로는 Q10과 다르므로 별도 질문이 필요하다.

- **Q10-b.** 이용자가 **본인 기기에서 실행하는 오픈소스 소프트웨어**가 본인 발급 API 키로 증권사에서 본인 체결내역을 읽어 당사 서버로 전송하는 구조. 당사는 증권사에 접근하지 않고 이용자가 전송한 데이터만 저장한다. 이것이 **본인신용정보관리업(마이데이터) 허가 대상**인지? 수기 입력·CSV 업로드와 법적으로 구분되는지?
- **Q10-c.** 같은 구조에서 당사가 그 소프트웨어의 **배포자**라는 점이 토스 Open API 약관 §5②의 "앱키 제3자 제공"에 해당하는지? (키는 이용자 기기를 떠나지 않으며, 토스는 이용자가 자기 키를 ChatGPT·Claude 등 외부 도구에 연동하는 것을 공식 안내함)
- **Q10-d.** 이용자가 업로드한 **증권사 거래내역 엑셀·체결 알림 스크린샷**을 파싱해 저장하는 행위의 법적 지위. 개인정보처리방침 기재 수준 외 추가 의무(예: 신용정보 처리 관련)가 있는지?
- **Q10-e.** 이용자가 Claude/ChatGPT 등 **자기 AI 도구**에 당사 MCP 서버를 연결해 거래를 기록하는 구조에서, 당사가 그 AI 도구의 증권사 API 호출에 대해 책임을 지는 범위?

## 7. 리스크와 방어

| 리스크 | 방어 |
|---|---|
| 파싱 오류가 그대로 거울에 반영 | Inbox 승인 단계 필수. confidence < 0.8은 필드 강조 |
| 스크린샷 속 계좌번호·잔고 | 추출 후 즉시 파기, 원본 미저장, 로그 마스킹(기존 4.6 규칙 재사용) |
| 토스 토큰에 스코프 없음 → CLI가 주문 가능 | GET allowlist를 CLI에 내장, 테스트로 강제. `TossReadOnlyViolation` 패턴 이식 |
| 토스 API 정식 오픈 지연 | Phase 1은 토스와 무관. Phase 2는 KIS로 먼저 검증 가능 |
| "자동화하면 기록 습관이 무너진다" | thesis 없는 승인 불가. 체결만 있는 항목은 거울에 안 뜬다 |
| CLI 오남용(타인 키 입력) | CLI는 단일 사용자 로컬 실행만 지원. 서버는 어떤 키도 받지 않음 |
