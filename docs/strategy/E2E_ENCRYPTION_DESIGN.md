## 0. 지금 어디까지 됐나 (2026-06-02 실측)

| 단계 | 보장 | 상태 |
|---|---|---|
| **at-rest 암호화** (서버 보관 키, AES-256-GCM) | DB 덤프·백업·읽기권한 계약자가 유저 글 못 읽음 | ✅ **완료** — `EncryptedText` + 키링. 13개 컬럼(매매이유·메모·worry·문의 등) |
| **키 로테이션 안전** | 키 교체해도 기존 데이터 복구 가능 | ✅ **완료** — `pqenc:{version}:` 키링 + `reencrypt_user_text.py` |
| **E2E** (유저 보관 키) | **회사·서버도 못 읽음** | 🟡 **본 문서 (미구현)** |

## 1. E2E 란 (한 줄)

암호화 **열쇠를 유저 기기 밖으로 내보내지 않는다.** 서버엔 암호문만 도착하고, 키가 없으니 회사가 **수학적으로** 못 읽는다. (카톡 비밀채팅·시그널 메신저 방식)

---

## 2. 🔴 핵심 블로커 — 우리는 OAuth 전용이라 "유저 비밀"이 없다

E2E 의 열쇠는 **유저만 아는 비밀**에서 파생돼야 한다. 그런데:

- PivoxQuant 인증 = **Google / Kakao OAuth 전용. 자체 비밀번호가 없다** (`routes/auth.py`, CLAUDE.md "Auth").
- OAuth 토큰은 *유저 비밀이 아니다* — 구글이 발급하고 회사 서버도 본다. 거기서 키를 파생하면 회사가 키를 알 수 있어 E2E 가 깨진다.
- 즉 **유저만 아는 비밀을 새로 도입하지 않으면 E2E 키를 만들 데가 없다.** → 이게 제품 결정(UX·복구·이탈 영향)이라 CEO 판단 필요.

> 결론: "암호화를 더 세게"는 코드 문제지만, **E2E 는 인증 모델 문제다.** at-rest 를 먼저 끝낸(완료) 이유.

---

## 3. 키를 어디서 얻나 — 4가지 옵션 (트레이드오프)

| 옵션 | 방식 | 장점 | 단점 / 위험 |
|---|---|---|---|
| **A. 암호화 passphrase** | OAuth 로그인과 **별도**로 유저가 암호문구 설정 → Argon2id로 키 파생 | 표준·확실. 서버는 절대 안 봄 | 가입 마찰 ↑. **분실 = 영구 손실**(회사 복구 불가). 베타 이탈 위험 |
| **B. 기기 보관 키** | WebCrypto `non-extractable` 키를 브라우저 IndexedDB에 생성 | 유저가 암기할 게 없음 | **다기기 동기화 불가**. 브라우저 데이터 삭제·기기 분실 = 손실. PWA(모바일 주력)와 충돌 |
| **C. Passkey PRF** | WebAuthn passkey의 PRF 확장으로 키 파생 | 최신·강력. 생체인증과 결합 | 브라우저/OS 지원 편차. iOS Safari 제약. 베타엔 이름. |
| **D. 하이브리드 에스크로** | 클라 키 + 서버 보관 **복구 에스크로**(봉인) | 분실 복구 가능 | "회사도 못 읽음"이 **부분 훼손**(에스크로 = 회사가 복구 경로 가짐). 정직성 카피와 충돌 |

**예비 권고**: 출시 후 **A(passphrase) opt-in** — 원하는 유저만 켜는 "추가 잠금". 기본은 at-rest. 분실 위험을 **유저가 명시 동의**하고 켜게. B/C 는 다기기·지원편차로 베타 부적합. D 는 정직성 포지션과 충돌.

---

## 4. 무엇을 E2E 하나 — 데이터 분리 (우리만의 해법)

전부 E2E 하면 **서버가 글을 못 읽어 "거울"(패턴 분석)이 죽는다.** 그래서 가른다:

| 데이터 | 서버가 읽어야 하나? | E2E 대상? |
|---|---|---|
| **속마음 자유서술** (매매이유 rationale / worry / 메모 / devil's advocate) | ❌ 서버 분석 불필요 (그대로 보여주기만) | ✅ **E2E 가능** |
| **거래 숫자·라벨** (shares·price·side·ticker·날짜) | ✅ 거울이 회전율·집중도·손익 계산하려면 필요 | 서버 보관 유지 |
| **점수/페르소나** | 폐기됨(점수화) / 익명집계만 | 해당 없음 |

✅ 검증됨(2026-06-02): 행동 거울(`services/behavior/*_mirror.py`)은 **거래 숫자만** 읽고 자유서술은 안 읽는다 → 자유서술만 E2E 해도 거울 무손상. **at-rest 가 이미 자유서술/숫자를 같은 `EncryptedText` 경로로 안 가르고 다 덮고 있어**, E2E 전환 시 "자유서술 컬럼만 클라 암호화로 승격"하면 된다.

## 5. 구현 스케치 (옵션 A 기준, 결정 후)

1. **키 파생**: 로그인 후 passphrase 입력 → `Argon2id(passphrase, salt=user-specific)` → AES-256-GCM 키 (브라우저 WebCrypto, 메모리에만).
2. **쓰기**: 자유서술을 브라우저에서 암호화 → 서버엔 `e2e:1:{ciphertext}` 만 전송. 서버 `EncryptedText`는 이미 암호문이라 **이중 암호화 그대로 저장**(서버는 내용 모름).
3. **읽기**: 서버가 `e2e:` 봉투를 그대로 반환 → 브라우저가 passphrase 키로 복호화해 렌더.
4. **마커 분리**: 서버측 `pqenc:` vs 클라측 `e2e:` 접두사로 구분. 서버는 `e2e:` 를 만나면 복호 시도 안 함(그냥 봉투 보관).
5. **복구**: 분실 = 불가 명시 동의. (옵션 D 선택 시에만 에스크로.)
6. **마이그레이션**: opt-in 켠 시점부터 신규 글만 E2E. 기존 at-rest 글은 그대로(서버 키로 읽힘) — 혼재 허용.

---

## 6. 왜 지금(베타) 안 하나

1. **OAuth-only** → passphrase 라는 새 비밀 도입 = 가입 마찰 + 이탈, 첫 100 유저엔 독.
2. **분실 = 영구 손실** UX 가 일반 투자자에게 위험(CS 폭탄).
3. **모바일 PWA 주력** ↔ 기기 보관(B)·passkey(C) 제약.
4. at-rest 로 **현실적 위협(DB 유출)은 이미 차단** — E2E 의 한계수익은 "악의적 운영자/영장" 시나리오인데, 1인·pre-launch 신뢰모델에선 우선순위 낮음.
5. 정직성 포지션상 **지금은 "서버 보관, 우리도 못 읽음은 다음 단계"라고 정직히 말하는 것**이 과잉약속보다 신뢰를 올림(research).
